# 货币战争羁绊优化器

提供网页和独立 CLI，只计算角色和星徽带来的羁绊人数。它先最大化所选任务完成数，再在完成数相同的方案中最小化星徽消耗，不优化战斗力、费用、角色数量或养成成本。没有后端、方案持久化、分享或导入导出功能。

## 网页使用

从首页打开「货币战争羁绊优化器」，或直接访问 `/currency-wars`。网页默认 13 槽、18 枚星徽、排除专家，全部 25 项目标任务开启。整个多方案请求固定使用 60 秒共享搜索预算，不提供时限输入。

配置使用 Astral UI 浅色面板，包含「目标任务」和「设置」两个页签。全部目标任务直接展示羁绊图标、名称和人数门槛，开关按稳定任务 ID 即时生效，不再使用选择弹窗或确认草稿。列表纵向滚动，上下边缘按剩余内容渐隐；关闭全部任务后提示并禁用开始。设置中的两个数量滑块分别允许 1～13 槽、12～39 枚星徽，专家默认不勾选。星徽预算是最大允许用量，无须用满。低槽位无法完成部分任务属于正常优化场景，不拒绝请求。切换页签保留配置，开始与取消操作始终位于面板底部。

求解仍在独立 Web Worker 执行，显示加载状态而不伪造百分比。等待期间可编辑条件，重复启动被禁用；取消直接终止 Worker，重新开始会创建新实例。离开页面释放运行实例。配置和语言变化不会自动求解。

每次最多返回三个独立验证的候选方案；多个候选时使用页签切换，单个候选省略切换栏。切换不重新求解，阵容、任务、星徽、配方及贡献成员整体更新，关闭旧角色详情。新有效批次默认选择方案一。候选顺序和筛选规则不变。

结果复用原有角色头像、费用背景和三个星徽槽。阵容网格左对齐，默认卡片宽 128px，手机宽 104px；仅在展示副本上按费用降序、形态 ID 升序排序。点击或键盘激活头像打开 PrimeVue 详情弹窗，保留固有羁绊、佩戴星徽、特殊新增羁绊、形态和特殊角色信息。两个 Astral UI Badge 显示完成任务／该次任务总数、使用星徽／该次预算，不读取尚未求解的新表单值。

目标结果列表保留图标、名称、实际／要求人数和文字完成状态。已激活羁绊列表整体直接展示，每条成员详情默认折叠；展开后只显示来自求解结果的贡献成员头像，姓名可通过 title 和 ARIA 获取，不重新推算羁绊来源。特殊机制仍可展开查看。白色单色羁绊图标在浅色面板中转换为深色，头像、星徽和材料保持原色。

页面不展示状态码、耗时分解、证明、求解界限或 Gap 等诊断详情，底层返回字段保持不变。未证明最优和模型警告直接可见。条件改变后保留旧批次并标记过期；新求解失败、无结果或取消时保留上次有效结果并标明历史状态。主动取消不保留本轮未返回的局部结果。

界面提示提供简体中文和英文，游戏专名继续沿用中文快照。桌面配置栏宽 340px，960～1099px 收至 300px，低于 960px 上下排列。主题只作用于显式标记的面板和详情弹窗，不修改网站 Header 或其他工具；接入和维护见下节。

## Astral UI 接入与同步

依赖为 `astral-ui: file:vendor/astral-ui`，源码包与 npm 锁文件一同纳入版本管理。全新环境只需 `npm ci`，不需要相邻 fork、额外构建产物或运行时网络。库使用 Vue peer dependency，与应用共用 Vue。

页面导入 `astral-ui/components` 和 `astral-ui/scoped-theme.css`。前者不加载全局主题，后者仅影响 `.h-theme`。不要改用默认入口，否则会加载全局 `theme.css`。业务局部变量位于页面的 `ui/theme.css`；传送至 body 的 PrimeVue Dialog 同样显式添加主题类。

来源 commit、文件 SHA-256、已有文件的未提交扩展补丁及新增源码清单保存在 `vendor/astral-ui/provenance.json` 和 `local-changes.patch`。本次基于 fork Commit `0dce0fad3bc993708d62598e315210adbcfb7373`，记录的哈希还包含未提交扩展，不能仅凭 commit 复现这些字节。上游声明保留，不为第三方源码推定许可证。

显式更新时先在本地 fork 修改组件、文档和测试，检查通过后执行：

```bash
npm run sync:astral-ui -- --source /path/to/local/astral-ui
npm run validate:astral-ui
```

同步脚本只操作本仓库的 vendor 快照，不修改来源仓库、不创建 Git 子模块、不自动提交或联网。同步后重新验证类型、测试、格式和构建并检查差异。普通安装、测试和构建不执行同步。

## 星徽需求

网页结果在目标任务列表后直接展示「星徽需求」。统计只遍历当前选中候选的 `lineup.members[].emblemIds`，按稳定星徽 ID 累加；仅展示实际使用项，按数量降序、ID 升序排列，总数等于该方案的 `evaluation.emblemCount`。切换方案即时更新，不重新求解；过期、历史或上次有效结果继续显示原候选的数据，不读取正在编辑的配置。零星徽方案显示空状态。

每行显示星徽图标、名称、需求数量及该赛季的全部合法合成配方。每条配方合成一个星徽，多条配方之间的「或」表示替代关系；例如欢愉星徽可使用垃圾袋与红钻，或垃圾袋与蓝钻，不需要同时消耗两组材料。没有当前赛季配方的星徽仍正常计数，合成区域仅显示 `—`；这只表示经过权威数据核对无配方，数据提取或校验失败会明确报错。

本功能不汇总材料总量，不处理库存、合成次数、差额、配方选择或最低成本。材料名称来自锁定游戏数据，所有图片使用本地资源；缺图时保留名称并显示中性占位。640px 及以下把配方放到该行下方，材料允许换行。

此功能仅扩充网页结果展示，CLI 的单方案输出与求解规则保持不变。

## 控制台使用

使用项目要求的 Node.js 24.x（最低 24.12）与 npm，按锁文件安装依赖后，从仓库根目录执行：

```bash
npm run currency-wars
```

TTY 终端会依次询问槽位、星徽预算、是否包含专家、任务子集和求解时限。通过命令行提供的选项不重复询问；非 TTY 自动使用非交互模式。

默认 13 槽、12 星徽、排除专家、30 秒。正式用户模式允许 1～13 槽；预算接受至少 12 的安全整数，不设人为上限，实际最多使用 `3 × 槽位` 个星徽。时限必须为正的有限秒数，是整个请求的时间预算，包含 Wasm 初始化、建模、求解和验证；允许少量不可避免的原生求解停止与调度开销。CLI 保留单方案输出，使用相同规则、验证器及预算实现。

```bash
npm run currency-wars -- --non-interactive --slots 13 --emblems 18 --time-limit 30 --select all
npm run currency-wars -- --tasks ./my-tasks.json --select task-001,3 --include-experts
npm run currency-wars -- --help
```

`--tasks` 路径相对当前工作目录解析；未指定时使用本仓库 `data/currency-wars/tasks.json`。`--select` 支持以逗号分隔的任务 ID、从 1 开始的编号或 `all`；先匹配任务 ID，再解析编号，重复选择只计一次。非交互模式默认选择全部任务。

结果显示求解状态、任务完成数、角色数量、星徽使用量、耗时，以及阵容、激活羁绊贡献者和逐项任务人数。角色与羁绊均带稳定 ID，羁绊同时标注阵营、流派或独立类型。

退出码：`0` 为成功输出最优／可行结果或空任务提示，`1` 为无结果／求解器报告不可行，`2` 为输入、数据、模型或结果验证错误。结果未通过独立验证时不会作为可用方案输出。可行但未证明最优的方案会明确标注；不会把超时等同于最优。

## 正式任务列表

`data/currency-wars/tasks.json` 已按用户提供的完整清单录入 25 项任务，保持原始顺序，稳定 ID 为 `task-001` 至 `task-025`。程序仍支持空列表：正常提示并退出，不启动求解器。

每项任务保存稳定 ID、羁绊数字 ID 和目标人数；以下为正式列表的前两项：

```json
[
  { "id": "task-001", "traitId": 1007, "requiredCount": 7 },
  { "id": "task-002", "traitId": 1008, "requiredCount": 6 }
]
```

任务 ID 必须为非空、无首尾空白且全文件唯一的字符串；羁绊 ID 必须存在，人数为正的安全整数。未知字段、重复任务 ID 和非法数据被拒绝。同一羁绊不同人数门槛可同时完成；超过可达人数的门槛保留为未完成。名称不能代替数字 ID。

技术演示任务单独保存在 `tests/fixtures/currency-wars/demo-tasks.json`，不代表真实游戏任务，不会复制进正式文件：

```bash
npm run currency-wars -- --non-interactive --tasks tests/fixtures/currency-wars/demo-tasks.json --slots 13 --emblems 12 --time-limit 5
```

2026-10-17 修正规则后的一次实际输出节选；阵容与耗时以本机实际执行为准：

```text
求解状态：已证明最优（本版保守模型） [optimal]
耗时：0.602 秒；请求时间预算：5 秒
完成任务：10 / 12
上场角色：13 / 13
使用星徽：11 / 12（自然上限 39）
加权目标上界：389；Gap：0
```

该次阵容中的椒丘佩戴列车同行、欢愉星徽，因列车同行星徽成为合法目标。姬子·启行选择椒丘后只取得其固有减益、持续伤害；她自身的护盾来自自己佩戴的护盾星徽，椒丘的欢愉星徽和狼狩阵营没有被继承。即使椒丘另戴护盾星徽，护盾也不会被继承；椒丘自身仍正常拥有全部固有及星徽羁绊。完整阵容和逐项任务可通过上述命令检查。

## 羁绊类型与规则

快照显式区分三类：`camp`（阵营）、`class`（流派）、`unique`（独立）。普通阵营与流派人数都按每名具有该羁绊的角色贡献 1 人计算，但类型在特殊机制中有严格差别。

| 类型 | 例子                                    | 姬子·启行能否继承                    |
| ---- | --------------------------------------- | ------------------------------------ |
| 阵营 | 列车同行 1001、仙舟 1007、盛会之星 1010 | 否                                   |
| 流派 | 能量 2004、减益 2007、持续伤害 2008     | 仅目标固有流派及开拓者明确授予的流派 |
| 独立 | 大守护者 3001、领航员 3007              | 否                                   |

星徽必须在快照中实际存在。每名上场角色最多三个，不能重复同种星徽、不能获得已有羁绊；同一种星徽可给不同角色佩戴，受全局预算限制。独立羁绊不虚构星徽补足。全部真实星徽都会进入候选，包括不直接对应目标任务、但能赋予领航员资格的列车同行星徽。

- **姬子·启行**可选择另一名上场角色作为目标；目标必须具有列车同行 1001，可以由固有羁绊或所佩戴星徽提供。选择后必须同时取得目标的全部固有流派，不是任意挑选其中一种；目标通过星徽新增的流派、阵营和独立羁绊均不继承。目标为任一开拓者形态（8007 或 8009）时，继承集合额外并入能量 2004 和欢愉 2012，不受其前后台固有流派互斥影响，也不要求目标佩戴另一流派星徽；合并后每种流派只继承一次。开拓者的其他流派星徽仍不被继承。若任一继承流派已由姬子自身或星徽取得，则整项配置非法，不用去重掩盖冲突；双方佩戴同一种未被继承的流派星徽则不构成继承冲突。允许不选择目标。
- **常规景元**仅允许 `1204`（5 费）进入候选；`12041`（1 费）、`12042`（3 费）仍如实保留于原始快照和费用目录。模型和独立校验器共用集中候选资格判断。
- **开拓者**的两个形态共用身份；前台固有能量，后台固有欢愉。可以佩戴另一流派星徽，同时获得两者，但不能把两个形态同时上场。
- **布洛妮娅**按其他角色的最终人数（包括星徽与合法领航员继承）比较贝洛伯格、燃血，排除自身的全部贡献，严格加入人数较多一侧。平局保留大守护者，两侧不计她的人数，并提示结果为保守下界；她的星徽必须在两种可能归属下都合法。平局模型中的 `11011:tie` 是工具状态，不是上游角色 ID。
- **初版禁止布洛妮娅成为领航员目标**。这是用户选定的限制，避免未确认的形态／继承反馈关系；即使给她列车同行星徽也不允许。
- **白厄**取得其他已激活羁绊效果不增加人数，故不计作那些羁绊的成员。其他战斗效果、复制首件装备和遭遇／模块修改不建模。

所有最优性证明只针对上述快照与本版规则。未知的游戏平局规则及禁止的目标组合意味着此原型不是所有游戏机制下的完整全局最优证明。

## 数据快照与显式提取

来源为 [TurnBasedGameData](https://github.com/DimbreathBot/TurnBasedGameData)，锁定 Commit `312b4597691e0a29cf9828a15b592757dba86949`，4.6.0、Season 1。保留既有[来源致谢](third-party/README.md)。快照包含 77 条原始角色配置、78 个规范化形态、71 个身份（排除专家后 62 个）、33 种羁绊和 22 种星徽。

`scripts/currency-wars/source-lock.json` 维护固定来源与审阅过的阵营 ID。此 Commit 中 `TraitType: "Class"` 为流派，`"Unique"` 为独立；阵营条目省略该字段，仅锁定名单中的缺省类型映射为阵营。未知类型、未审阅切换与不支持的星徽规则会阻止提取，不从中文名称或数字范围推断类型。

提取读取 GridFight 角色、羁绊、星徽、门槛、形态、效果调查表、物品名、AvatarConfig／AvatarConfigLD 与中文 TextMap。Hash 从 JSON 原始整数词法保存为字符串。身份按相同 AvatarID 及显式切换关系合并；不会把不同 AvatarID 的剧情人物形态擅自合并。

正常求解、安装、测试、构建不联网、不读取相邻仓库，也不自动生成数据。显式维护命令：

```bash
npm run validate:currency-wars
npm run extract:currency-wars -- --root ../TurnBasedGameData
```

提取要求来源是干净的 Git 根目录且 HEAD 等于锁定 Commit，不 fetch 或切分支，只写本工具的快照和 Manifest；**不会写入或清空任务文件**。Manifest 记录输入文件 SHA-256、来源、转换版本、规则说明、统计和输出哈希。提取后审阅变更并执行快照检查、相关测试。生成 JSON 用固定序列化，不能交给 Prettier 改写。

### 独立展示数据

网页另用 `data/currency-wars/visuals.json` 和 `visuals-manifest.json`，没有修改算法快照或 `RoleForm`。费用来自同一来源 Commit 的 `GridFightRoleBasicInfo.Rarity`，通过 `GridFightShopPrice.BuyGoldStar1` 确认 1–5 费对应关系；按形态 ID 保存，银狼 LV.999、景元的多种配置可以共用头像但费用不同。布洛妮娅的平局工具状态使用其基础配置费用。

头像默认使用 `RoleForm.avatarId`，开拓者 `8007`、`8009` 的展示映射显式共用已目视确认的本地星头像 `character/8008.webp`，角色 ID、费用与羁绊不变。星徽使用从装备 ID 查得的 `Emblem.traitId`；可选 `traits` 映射使用羁绊数字 ID 指向 `public/game-assets/currency-war-traits/{id}.webp`。这些羁绊图标由用户提供，独立于锁定的上游费用数据；当前有 32 个，缺少 `1014（师徒）`，未建立虚假映射，不影响求解或当前 25 项任务的图标。所有映射检查现有本地文件，运行 URL 兼容 `BASE_URL`。图片失败会显示中性占位并保留名称。费用仅用于展示，从不进入请求或优化目标。

展示 Manifest 转换版本为 3，保存来源文件、算法快照、输出和映射图片（包括羁绊图标）的 SHA-256，并单独说明羁绊图片来自用户本地资源；目录 schemaVersion 仍为 1，旧目录没有 traits 时界面使用占位。补入缺失图标后，显式执行下面的展示提取命令更新映射与哈希，不会自动根据文件名生成未经记录的 URL。只有显式生成命令读取上游，不更改已有图片、算法数据或任务。普通检查、测试和构建使用仓库内展示数据：

```bash
npm run extract:currency-wars-visuals -- --root ../TurnBasedGameData
npm run validate:currency-wars-visuals
```

### 星徽合成目录与材料资源

独立的 `data/currency-wars/crafts.json`／`crafts-manifest.json` 仅用于展示，不扩展算法 `Emblem`、角色快照或任务文件。目录版本为 1，明确记录 Season 1；对每种快照星徽保留一个配方数组，无当前赛季配方时使用空数组，缺少目录键视为错误。

显式提取使用同一 Source Lock 的 `GridFightCraftConfig`、`GridFightSeasonCraft`、`GridFightEquipment`、`GridFightItems` 与中文 TextMap。先以 `CraftID` 和 `SeasonID` 过滤赛季，再以 `CraftEquipID` 关联星徽装备 ID；材料不局限于 Basic 装备或钻石，垃圾袋也按真实物品 ID 和名称保留。名称 Hash 复用精确整数词法解析，不经 JavaScript Number 转换。

同产物不同材料配方全部保留；仅材料顺序不同的等价多重集合合并，并用 `craftIds` 保留所有来源配方 ID。两件相同材料不会被误去重为一件。当前锁定数据核对为 22 种星徽、17 种可合成、18 条配方；欢愉星徽 `35052012` 保留 CraftID 57、58 两条替代配方。这些数量是该来源的结果，不是永久 Schema 限制。

```bash
npm run extract:currency-wars-crafts -- --root ../TurnBasedGameData

```

### Worker 与 WASM

浏览器 Worker 调用 `solveCurrencyWarsBatch`，CLI 的 `solveCurrencyWars` 是相同编排的单方案兼容包装。通过 `createHighsSolver(loader)` 仅替换 HiGHS 加载方法。求解选项、状态解释、解码与独立验证没有另写一套。每次运行通过结构化消息传递请求与结果，带运行 ID，旧实例响应不会覆盖新状态。

Vite 以 ES module 打包 Worker，通过 `highs/runtime?url` 输出带哈希的本地 WASM；浏览器适配器向 HiGHS 提供 `locateFile`。WASM 只在用户发起求解时由 Worker 初始化，不从 CDN 下载。根路径与子路径构建均可使用。

构建时可能看到 highs 包中受环境分支保护的 `node:module` 外置化提示，以及同包静态／动态导入提示；浏览器分支不会执行 Node 加载逻辑，也没有添加 Node polyfill。用以下探针实际执行构建产物和 WASM，不能仅凭 build 成功判断初始化可用：

```bash
npm run build
npm run verify:currency-wars-browser
npm run build -- --base /hsr/ --outDir .cache/currency-wars-subpath
npm run verify:currency-wars-browser -- --dist .cache/currency-wars-subpath --base /hsr/
```

探针在独立 Node 线程的无 Node 全局 VM 中执行真实浏览器 Worker 代码，fetch 只读取本地构建的 WASM，验证结果及主线程心跳；它不启动浏览器，不等同于浏览器人工验收。HiGHS 许可证逐字保留于 `public/third-party/highs-LICENSE.txt` 并进入静态产物。

## 核心接口与验证

`src/tools/currency-wars/` 提供 `Snapshot`、`Task`、`OptimizationRequest`、`Lineup`、`Evaluation`、`CandidateSolution`、`OptimizationBatch` 和兼容的 `OptimizationResult` 类型，以及纯函数 `buildModel`、`evaluateLineup` 和异步批次／单方案入口。请求携带任务、槽位、预算、专家开关与时限；确定阵容携带形态 ID、星徽 ID 和可选领航员目标形态 ID。

模型和计算器不读取文件、原始配置、Vue 或 CLI。计算器独立于 LP 约束实现；返回错误、警告、每名角色的羁绊来源、每个羁绊的贡献者／门槛、任务完成结果和目标值。求解封装另外核对模型人数、任务标志和目标值，拒绝不完整／非整数／不一致的结果。

HiGHS 1.15.3 通过 Wasm 在本地求解 MILP，目标为 `(3S + 1) × 完成数 − 星徽数`，相对与绝对 MIP Gap 均为零。受限求解需检查 `primal_solution_status` 才能读取 incumbent。批次证明结合已排除的全部有效配置和剩余搜索空间：不能仅凭某个子问题为 optimal 就将该候选称为原问题全局最优。完成全部所选任务可以单独证明最大完成数，但不能据此证明星徽最少。候选的 `originalOptimal` 还须达到原问题已证明的最优加权目标。每个候选核对全部二元列、模型约束、实际人数、任务标志及目标值；不放宽整数容差。测试中的穷举只用于小规模 Oracle。

### 多方案搜索与时间预算

采用重复 HiGHS MILP 求解加完整配置 No-good Cut。只对角色形态、每角色每类星徽分配和领航员目标变量排除配置，包含取值为零的决策；任务标志不参与。领航员继承由目标选择变量直接决定，不再为目标星徽构造继承 AND 辅助变量。canonical signature 对角色及星徽集合排序，忽略显示顺序和星徽槽顺序，保留分配关系、形态和领航员目标；结果层再次去重。模型构建器生成约束，不拼接外部 LP 内容。

尚未证明最大完成数时，以当前最好完成数作为搜索下界，允许后续找到更多任务；发现更高值后清除较低完成数的可见候选，但保留其排除记录和证明证据。证明最大完成数后将其固定。不会为了补足三个方案接受更低完成数。

所有步骤共用单调 deadline。多方案首轮分配当前剩余预算的 75%；已有一个候选时下一轮用剩余一半，已有两个时用剩余全部。首轮没有 incumbent 时，用余下全部预算优先恢复首个结果。提前结束的时间自动留给后续搜索，达到三个合格候选、配置穷尽或预算耗尽即停止。单方案包装直接使用全部剩余预算。HiGHS runtime 在适配器内惰性缓存，运行前扣除加载与模型解析时间，每个原生模型在 finally 释放。

批次保留脱离编辑表单的请求快照；Session 管理统一的 selectedSolution 和合法选择索引，继续使用请求 ID、lastAttempt、lastValid、stale、historical。错误／取消不替换上次有效批次。
